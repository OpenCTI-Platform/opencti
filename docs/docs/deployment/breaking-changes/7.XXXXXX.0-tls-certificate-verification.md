# TLS certificate verification enabled by default

!!! info ""

    * **Changed in**: `OpenCTI 7.XXXXXX.0`

## Description of changes

Outgoing TLS connections now **verify the server certificate by default**. Before this version, many of them accepted any certificate (self-signed, expired, issued for another host), which exposed them to man-in-the-middle attacks.

After the upgrade, a connection to a server whose certificate is not trusted fails, unless certificate verification is explicitly disabled for it.

### Platform

A new global option controls certificate verification for every outgoing TLS connection of the platform:

| Parameter                 | Environment variable       | Default value |
|:--------------------------|:---------------------------|:--------------|
| `tls:reject_unauthorized` | `TLS__REJECT_UNAUTHORIZED` | `true`        |

It is used as a fallback: a connection that defines its own option keeps using it, and a connection without one follows the global option.

| Connection                                                                      | Specific option (overrides the global one)                       | Before      |
|:--------------------------------------------------------------------------------|:-----------------------------------------------------------------|:------------|
| RSS, CSV, JSON and TAXII feeds, synchronizers                                   | "Verify SSL certificate" of each feed                            | Not verified when the option was not set |
| SMTP                                                                            | `smtp:reject_unauthorized`, or the SMTP configuration in the UI | Not verified |
| RabbitMQ                                                                        | `rabbitmq:use_ssl_reject_unauthorized`                           | Not verified |
| RabbitMQ management plugin                                                      | `rabbitmq:management_ssl_reject_unauthorized`                    | Not verified |
| HTTPS proxy                                                                     | `https_proxy_reject_unauthorized`                                | Not verified |
| Credentials provider (CyberArk)                                                 | `{prefix}:credentials_provider:https_cert:reject_unauthorized`   | Not verified |
| Filigran services: XTM One (chatbot, AI agents in playbooks), XTM Hub, telemetry, connector catalog | None, only the global option                   | Not verified |

Not affected:

- Feeds and synchronizers where "Verify SSL certificate" was explicitly disabled keep their setting. Synchronizers created from the UI before this version were saved with verification **disabled**: review them and enable verification where possible.
- Webhooks and Elasticsearch / OpenSearch already verified certificates.

### Python client, workers and connectors

The global option `tls:reject_unauthorized` only applies to the platform. Workers, connectors and scripts using the Python client have their own options, whose default value changes from `false` to `true`:

| Parameter                        | Environment variable             | Usage                                                         |
|:---------------------------------|:---------------------------------|:--------------------------------------------------------------|
| `opencti:ssl_verify`             | `OPENCTI_SSL_VERIFY`             | Verify the certificate of the OpenCTI platform                |
| `mq:use_ssl_reject_unauthorized` | `MQ_USE_SSL_REJECT_UNAUTHORIZED` | Verify the certificate of RabbitMQ                            |
| `worker:listen_api_ssl_verify`   | `WORKER_LISTEN_API_SSL_VERIFY`   | Verify the certificate of connectors running in HTTP mode     |

In scripts, the `ssl_verify` parameter of `OpenCTIApiClient` now defaults to `True`.

## Migration guide

### Recommended: trust your certificates

If one of your services uses a certificate issued by an internal certificate authority, provide this authority instead of disabling the verification:

- **Platform**: depending on the connection, the authority is provided either with `NODE_EXTRA_CA_CERTS=/path/to/ca.pem` or with a dedicated option:

    | Connection                                   | Certificate authority option                                                                    |
    |:---------------------------------------------|:------------------------------------------------------------------------------------------------|
    | Feeds, synchronizers, SMTP, Filigran services | `NODE_EXTRA_CA_CERTS`                                                                           |
    | RabbitMQ (AMQP connection)                   | `rabbitmq:use_ssl_ca`                                                                           |
    | RabbitMQ management plugin                   | `NODE_EXTRA_CA_CERTS` (`rabbitmq:use_ssl_ca` does not apply)                                    |
    | HTTPS proxy                                  | `https_proxy_ca`                                                                                |
    | Credentials provider (CyberArk)              | `{prefix}:credentials_provider:https_cert:ca` when a client certificate (`https_cert:crt`) is configured, `NODE_EXTRA_CA_CERTS` otherwise |

- **Python client, workers and connectors**: `OPENCTI_SSL_VERIFY=/path/to/ca.pem` to reach the platform, `MQ_USE_SSL_CA=/path/to/ca.pem` to reach RabbitMQ.

### Not recommended: restore the previous behavior

Certificate verification can be disabled at your own risk, globally or per connection.

Platform, for every connection without a specific option:
```shell
TLS__REJECT_UNAUTHORIZED=false
```
or
```json
{
  "tls": {
    "reject_unauthorized": false
  }
}
```

Platform, for one connection only, for example SMTP:
```shell
SMTP__REJECT_UNAUTHORIZED=false
```

Python client, workers and connectors:
```shell
OPENCTI_SSL_VERIFY=false
MQ_USE_SSL_REJECT_UNAUTHORIZED=false
WORKER_LISTEN_API_SSL_VERIFY=false
```
